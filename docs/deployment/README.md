# Deploying Esoqo

This is the operational runbook for both environments. It is meant to be
followed literally — if a step here is wrong, fix the step, not just the
cluster.

> **Read `CONTRIBUTING.md` §3 first.** The GitOps flow this file
> describes (push → Actions builds images → Fleet applies them) is not
> currently operating — GitHub Actions is broken at the platform level
> and Fleet's actual connection state is unconfirmed. Every real deploy
> right now is `deploy/scripts/build-and-push.sh` followed by a manual
> `kubectl apply -k`. The architecture below is still the intended
> target state and the manifests are correct; just don't expect a git
> push alone to do anything to the cluster yet.

---

## 1. The model in one paragraph

**A deploy is a commit.** Pushing to `preview` builds images, writes
the new image tags into `deploy/k8s/overlays/preview/kustomization.yaml`,
and commits that back. Rancher Fleet watches the branch and applies the
result to the cluster. Production works identically from the `production` branch. Nothing deploys by running `kubectl apply` at a laptop, and
Fleet's drift correction will revert anything that tries. A rollback is
therefore `git revert`, and "what is running?" is answered by reading the
overlay at that branch's HEAD.

Each release is also published to the repository's **Deployments** tab:
`orchestrate.sh` opens a GitHub Deployment for the environment
(`preview`/`production`) at the deployed SHA and posts `in_progress` →
`success`/`failure` statuses. This is best-effort — a failure to publish
never blocks or fails the deploy itself.

| | preview | production |
|---|---|---|
| Branch | `preview` | `production` |
| Namespace | `preview` | `production` |
| Overlay | `deploy/k8s/overlays/preview` | `deploy/k8s/overlays/production` |
| Apex host | `preview.esoko.global` | `esoko.global` |
| SMS | `console` — logs, never sends | **live** |
| Payments | sandbox | **live** |
| Replicas | 1 each | 2 (1 for admin) |
| Postgres volume | 20Gi | 100Gi |

## 2. What runs

Seven workloads plus three stateful pieces, all in one namespace per
environment.

| Workload | Image | Port | Hostname (preview) |
|---|---|---|---|
| `web` | `esoqo-web` | 3000 | `preview.esoko.global` |
| `app` | `esoqo-app` | 3001 | `preview-app.esoko.global` |
| `admin` | `esoqo-admin` | 3002 | `preview-admin.esoko.global` |
| `store` | `esoqo-store` | 3003 | `preview-store.esoko.global` |
| `jamii` | `esoqo-jamii` | 3004 | `preview-jamii.esoko.global` |
| `core-service` | `esoqo-core-service` | 4000 | `preview-api.esoko.global` |
| `core-go` | `esoqo-core-go` | 4100 | `preview-mobile.esoko.global` |
| `postgres` | `postgres:16-alpine` | 5432 | *(in-cluster only)* |
| `pgbouncer` | `edoburu/pgbouncer` | 6432 | *(in-cluster only)* |
| `redis` | `redis:7-alpine` | 6379 | *(in-cluster only)* |

Apps connect through **PgBouncer** (`DATABASE_URL`). Prisma migrations,
`pg_dump` and the audit-chain walk connect **directly** to Postgres
(`DIRECT_DATABASE_URL`) because none of them survive transaction
pooling. Both URLs are generated by `create-secrets.sh` — do not
hand-write them.

## 3. One-time setup

Do this once per environment. It is the only part involving a browser.

### 3.1 Cluster prerequisites

In Rancher (<https://rancher.2lovelaces.io/>), on the target cluster:

0. **Check your own permissions first.** A Rancher kubeconfig carries
   only the rights your Rancher role grants, and a restricted role
   produces a kubeconfig that authenticates fine and then refuses
   everything — which reads like a broken manifest rather than a
   missing role. Verify before anything else:

   ```bash
   export KUBECONFIG=<downloaded kubeconfig>
   kubectl auth can-i create deployments --all-namespaces
   kubectl auth can-i create gitrepos.fleet.cattle.io -n fleet-default
   ```

   Both must print `yes`. If either prints `no`, you need the
   **Cluster Owner** role on this cluster (Rancher → Cluster → Members),
   or an admin-issued kubeconfig. Nothing below will work without it.

   Note that Fleet applies manifests with its OWN service account, so
   the GitRepo permission is what matters for ongoing deploys — but you
   still need workload permissions to run the preflight, create the
   secrets, and debug a bad rollout.

1. **Label the cluster.** Cluster → Edit Config → Labels. Add
   `env=preview` (or `env=production`). The Fleet `GitRepo` selects on
   this label rather than naming the cluster, so replacing the cluster
   later does not mean editing the repo.
2. **Install ingress-nginx** if the cluster has no ingress controller.
   RKE2 ships one; k3s ships Traefik instead. Check:
   ```bash
   kubectl get ingressclass
   ```
   If the class is not named `nginx`, change `ingressClassName` in both
   overlays' `ingress.yaml` and in
   `deploy/cluster/cluster-issuer.yaml` to match.
3. **Install cert-manager.** Apps → Charts → cert-manager, with the
   "Install CRDs" option enabled.

### 3.2 ClusterIssuers — superseded, see below

```bash
kubectl apply -f deploy/cluster/cluster-issuer.yaml
```

Both `letsencrypt-staging` and `letsencrypt-prod` are created. Start on
staging — see [§9](#9-tls-and-wildcards).

**This needs cluster-admin and the account available for day-to-day
work has never had it** (confirmed 2026-09-27 — same finding as §3.9's
account). `ClusterIssuer` is cluster-scoped; a namespace-scoped account
can't create, read, or even list it, which is why this looked like a
silent, unexplained TLS failure for days rather than a permissions
error. **The actual fix in place on both environments now is a
namespaced `Issuer`** — same ACME account flow, same HTTP-01 solver,
needs only the same per-namespace rights as everything else in the
overlay. See `deploy/k8s/overlays/{preview,production}/issuer.yaml` and
the ingress annotation `cert-manager.io/issuer` (not
`cluster-issuer`). If you ever do get a cluster-admin kubeconfig, the
`ClusterIssuer` approach above still works and is arguably cleaner
long-term — but don't assume you have the access to use it.

### 3.3 Git credentials for Fleet

The repo is private, so Fleet needs read access. Create a GitHub
fine-grained PAT with **Contents: read** on `esoko-254`, then, on the
**Rancher local cluster**:

```bash
kubectl -n fleet-default create secret generic esoqo-git-credentials \
  --from-literal=username=Emmanuel-Odero \
  --from-literal=password='<the-PAT>'
```

### 3.4 Register the GitRepo

Also on the Rancher local cluster:

```bash
kubectl apply -f deploy/fleet/gitrepo-preview.yaml
# later, when production is ready:
kubectl apply -f deploy/fleet/gitrepo-production.yaml
```

Watch it in Rancher → **Continuous Delivery → Git Repos**.

### 3.5 Secrets

```bash
cp deploy/scripts/secrets.env.template ~/preview.secrets.env
# fill it in — every "required" field
deploy/scripts/create-secrets.sh preview ~/preview.secrets.env
```

The script validates before touching the cluster, builds the connection
strings, and prints the kube context for confirmation first. Store the
filled-in file in a password manager and delete it from disk.

> `AUDIT_CHAIN_SEED` is set **once per environment and never rotated**.
> Changing it breaks the existing hash chain permanently and
> `audit:verify` will fail forever after. preview and production must
> have different values.

### 3.6 DNS at Cloudflare

The `esoko.global` zone is on Cloudflare. Open Cloudflare → `esoko.global`
→ **DNS → Records**. Preview hosts are single-label
(`preview-app.esoko.global`, not `app.preview.esoko.global`) because the
zone's bridge certificate covers only one level below the apex
(`esoko.global` + `*.esoko.global`); two-level names cannot be proxied on
the Free plan. Records must be **Proxied** (orange cloud) so Cloudflare
Access can gate them.

First get the ingress IP:

```bash
kubectl get svc -A \
  -o jsonpath='{range .items[?(@.spec.type=="LoadBalancer")]}{.metadata.namespace}/{.metadata.name} {.status.loadBalancer.ingress[0].ip}{"\n"}{end}'
```

If that is empty, the controller is `NodePort` rather than
`LoadBalancer` — use a worker node's public IP instead:

```bash
kubectl get nodes -o wide
```

Then add one **Proxied** A record per host:

| Type | Name | Content | Proxy |
|---|---|---|---|
| A | `preview` | `<INGRESS_IP>` | Proxied |
| A | `preview-app` | `<INGRESS_IP>` | Proxied |
| A | `preview-admin` | `<INGRESS_IP>` | Proxied |
| A | `preview-store` | `<INGRESS_IP>` | Proxied |
| A | `preview-jamii` | `<INGRESS_IP>` | Proxied |
| A | `preview-api` | `<INGRESS_IP>` | Proxied |
| A | `preview-mobile` | `<INGRESS_IP>` | Proxied |

The apex `esoko.global` stays **DNS-only** and keeps its redirect to
`esoqo.com`; proxying it would break that redirect.

And for production, when you get there:

| Type | Host | Value | Proxy |
|---|---|---|---|
| A | `@` | `<INGRESS_IP>` | Proxied |
| A | `www` | `<INGRESS_IP>` | Proxied |

> The apex **must** be a DNS A record. DNS forbids a CNAME at a zone apex,
> and a redirect-based apex breaks the ACME HTTP-01 challenge, so
> certificates will never issue.

Verify before expecting TLS to work — cert-manager cannot succeed until
these resolve publicly:

```bash
dig +short preview.esoko.global
dig +short preview-admin.esoko.global
```

### 3.7 GHCR package visibility

The first push creates the packages as **private**, and the cluster
cannot pull them. Use a pull secret.

> ⚠  Do **not** resolve this by making the packages public.
> `esoqo-core-service` ships the entire workspace at `/repo` —
> TypeScript source for every app and package, because tsx compiles at
> runtime (see `docker/Dockerfile.core`). Publishing that package
> publishes the source. The Next images are less exposed but still
> carry traced server code. Private packages plus a pull secret is the
> only correct answer here.

Create the pull secret in each namespace:

```bash
kubectl -n esoqo-preview create secret docker-registry ghcr \
  --docker-server=ghcr.io \
  --docker-username=Emmanuel-Odero \
  --docker-password='<PAT with read:packages>'
kubectl -n esoqo-preview patch serviceaccount default \
  -p '{"imagePullSecrets":[{"name":"ghcr"}]}'
```

`ImagePullBackOff` on the first deploy is almost always this.

### 3.8 Branch protection

**Do not skip this for production.** `build-images.yml` runs in parallel
with `ci.yml`, so it is branch protection — not the workflow — that
stops untested code from shipping.

GitHub → Settings → Branches → add a rule for `production`:

- Require a pull request before merging
- Require status checks to pass: `verify`, `security`
- Do not allow bypassing

Then add a `DEPLOY_BOT_TOKEN` secret (a PAT that may push to the
protected branch), so the tag-bump commit can land.

### 3.9 First bootstrap of `preview` (Sept 2026) — what actually happened

§3.1–§3.8 describe the intended one-time setup. None of it had been done
when `preview` was first brought up, and the account available for the
job turned out not to have the rights §3.1 assumes. This section is a
record of the actual path taken — read it before repeating any of §3.1–§3.8
by hand, because some of their assumptions are wrong for this cluster as
provisioned today.

**Fleet was never installed.** `GET /v1/fleet.cattle.io.gitrepos` against
the Rancher API returned a flat `404` — not "no GitRepo yet", but "the CRD
doesn't exist". Nothing in §1's git-driven model was running; every
image tag sitting in the overlay was inert until something applied it by
hand.

**The available Rancher account was project-scoped, not cluster-admin.**
`kubectl auth whoami` identified it as `genericoidc_group://esoqo`, and
`kubectl auth can-i create deployments --all-namespaces` printed `no`.
`can-i create deployments -n esoqo-preview` printed `yes` — full
namespace-admin, but nothing cluster-scoped (no ClusterIssuers, no
IngressClasses, no Fleet CRDs, no cluster labels). §3.1's preflight
should include the namespace-scoped check too:

```bash
kubectl auth can-i create deployments -n esoqo-preview
```

If that's `yes` but the cluster-wide one is `no`, you're in the same
position this bootstrap was: able to ship into the namespace, unable to
do any of §3.1–§3.4. Bootstrapping Fleet properly is still an open item —
it needs a cluster-admin kubeconfig, which nobody had at the time.

**The real namespace is `esoqo-preview`, not `preview`.** Whoever
provisioned the Rancher project ahead of time named the namespaces
`esoqo-preview` / `esoqo-production`, not the bare `preview` / `production`
that `deploy/k8s/overlays/*/kustomization.yaml` and most commands in this
doc assume. The preview overlay's `namespace:` field has been corrected
to match; commands elsewhere in this doc that say `-n esoqo-preview` need the
same substitution until the doc itself is fully reconciled.

**The ingress class is Traefik, not nginx** — confirmed empirically, not
just inferred from "k3s ships Traefik" (§9a). An `Ingress` with
`ingressClassName: nginx` got a generic, controller-less 404 from every
node; patching it to `traefik` routed correctly to a live backend within
seconds. Both overlays and `deploy/cluster/cluster-issuer.yaml` have been
updated. §9a's table of lost nginx-annotation behavior (body size limit,
www-redirect, noindex) still applies and is not yet re-implemented as
Traefik `Middleware` resources.

**Deploys went in via `kubectl apply`, not Fleet — by necessity, and
through the browser.** With no cluster-admin kubeconfig available, there
was no way to get a stable local `kubectl` session either (Rancher only
issues kubeconfigs scoped to what the requesting account can already do,
which was namespace-only). Everything was applied through Rancher's own
UI, in the `local` cluster's cluster-explorer:

- The embedded **kubectl shell** (terminal icon, top nav) works for
  short commands, but its websocket disconnects silently and often —
  including mid-command, with no error — which makes it unfit for
  anything long enough to matter (a `kubectl create secret` with a
  connection string, say).
- **Import YAML** (upload icon, top nav → "Read from File") proved
  completely reliable by comparison: pick a `Default Namespace`, upload
  or paste a manifest, click Import. It performs a real `kubectl apply`
  server-side, has no line-length or duration limit, and doesn't share
  the shell's disconnect problem. For anything beyond a one-line
  command, render the manifest locally and import it this way rather
  than typing it into the shell.
- Secret values were computed locally (`openssl rand -hex 24/32` per
  `secrets.env.template`), then either applied as a small `Secret`
  manifest via Import YAML, or patched onto the existing secret with
  `kubectl patch secret ... --type merge -p '{"data": {...}}'` — merge
  patch only touches the keys named, so it can't accidentally wipe
  unrelated ones the way a full re-`apply` of a partial Secret might.
- `deploy/scripts/create-secrets.sh` could not be run as-is — it expects
  an interactive `kubectl config current-context` confirmation from a
  real terminal, which the browser shell can't reliably hold open for.
  The secrets it would have created were built by hand, matching its
  logic exactly (see the script for the `DATABASE_URL` /
  `DIRECT_DATABASE_URL` construction).
- One-off diagnostic or repair work (see below) went in as scratch
  `Job` manifests running `postgres:16-alpine`, importing the SQL as a
  base64-encoded `echo | base64 -d | psql` one-liner — the same
  Import-YAML path, not the shell.

**Images built locally came out `arm64`-only, and the cluster is
`amd64`.** GitHub Actions is broken for this account (returns
`startup_failure` before any job is created — unrelated to this deploy,
not billing, not the workflow YAML) so `build-and-push.sh` ran from a
laptop instead. Plain `docker build` targets the host architecture, and
the laptop is Apple Silicon. The symptom was
`no match for platform in manifest: not found` in every app pod's
events. Fix: rebuild explicitly for the cluster's architecture and push
under the same tag —

```bash
docker buildx build --platform linux/amd64 \
  --file docker/Dockerfile.next --tag ghcr.io/emmanuel-odero/esoqo-web:<tag> \
  --push --build-arg APP=web --build-arg PORT=3000 .
```

— repeated per image. `build-and-push.sh` does not do this yet; if a
future run needs a non-native architecture, add `--platform` there
rather than rediscovering this by hand.

**Two real application bugs were hit and fixed, not deploy
misconfiguration:**

1. `packages/db/prisma/migrations/20260924000000_migrate_parcel_orgs_to_generic/migration.sql`
   referenced `po."settlementDays"` and `po."allowsWalkIn"` — neither
   column exists on `ParcelOrg` (the real ones are `settlementPhone` and
   `acceptsWalkIn`). `prisma migrate deploy` failed on this, the last of
   113 migrations, with a cascading `current transaction is aborted`
   that hid the real error; the actual `column ... does not exist` only
   showed up running the SQL directly against Postgres. Fixed in place
   in the migration file — it had never successfully applied anywhere,
   so editing it is safe (Prisma treats an unapplied migration's
   checksum as free to change).

   Because a prior failed attempt had already written a `failed` row for
   this migration into `_prisma_migrations`, the fix couldn't just be
   re-run through `migrate deploy` — Prisma refuses to proceed past a
   `P3009` "found failed migrations" state. The unblock was: run the
   corrected SQL directly, then replace the `_prisma_migrations` row
   with one recording it as applied, using the sha256 checksum of the
   now-fixed file (the same value `prisma migrate resolve --applied`
   would compute). A subsequent full `prisma migrate deploy` run then
   confirmed all 113 migrations apply cleanly against a fresh database
   using this fix.

2. `core-go` was in a permanent `CrashLoopBackOff`:
   `10.43.151.51:6432 (pgbouncer): server error: FATAL: unsupported
   startup parameter: connection_limit`. `core-go`'s Postgres driver
   (`pgx`) is not Prisma — it forwards every `DATABASE_URL` query-string
   parameter straight through as a real wire-protocol startup parameter,
   so Prisma's own `pgbouncer=true&connection_limit=10` hints made
   PgBouncer reject the connection outright, and `pgx` separately
   attempts TLS unless told `sslmode=disable`.
   `docker-compose.yml` already documents and works around exactly this
   for local dev (`core-go` gets its own `DATABASE_URL` there); the k8s
   manifests never got the equivalent. Fixed by adding
   `CORE_GO_DATABASE_URL` / `CORE_GO_DIRECT_DATABASE_URL` to
   `create-secrets.sh`'s output and overriding `core-go`'s `env:` in
   `deploy/k8s/base/core-services.yaml` to use them (`env:` wins over
   `envFrom:` for the same key, so this doesn't disturb `core-service`,
   which still reads the Prisma-flavored `DATABASE_URL` via `envFrom`).

**End state:** all 7 workloads (`web`, `app`, `admin`, `store`, `jamii`,
`core-service`, `core-go`) `Running` and passing `/health`; all 113
migrations applied; every preview hostname (`preview.esoko.global`,
`preview-app.esoko.global`, …) routing correctly over plain HTTP. **Not done:** TLS — the `letsencrypt-prod`
ClusterIssuer does not exist on the cluster (confirmed via
`CertificateRequest` status: `Referenced "ClusterIssuer" not found`),
and creating one is cluster-scoped, i.e. blocked on the same missing
cluster-admin access as Fleet itself. `kubectl apply -f
deploy/cluster/cluster-issuer.yaml` from an admin kubeconfig is all that's
needed once one is available. Also not done, and out of scope for a
preview bootstrap: the Fleet/GitOps install itself (§3.3–§3.4), the
production DNS cutover, and the Postgres data migration off the previous PaaS.

## 4. Routine deploy to preview

```bash
git checkout preview
git pull
# ... work ...
git commit -m "feat(parcels): ..."
git push
```

That is the whole procedure. Then watch:

1. **GitHub → Actions → "Build and deploy"** — seven images build in
   parallel, then `bump` commits the new tags. ~8–12 min cold, ~3–4 min
   warm.
2. **Rancher → Continuous Delivery → Bundles** — `preview` goes
   `Modified` → `Ready` within the 60s poll.
3. Confirm:
   ```bash
   kubectl -n esoqo-preview get pods
   kubectl -n esoqo-preview rollout status deploy/web --timeout=5m
   curl -sS https://preview.esoko.global/api/health
   ```

### Deploying without GitHub Actions

Fleet reads manifests straight from git, so Actions was never on the
critical path — it only builds the images and commits the tag bump.
`deploy/scripts/build-and-push.sh` does both from a laptop:

```bash
git checkout preview        # the script refuses to run from another branch
deploy/scripts/build-and-push.sh preview
git push origin preview     # this is what Fleet reacts to
```

The output is identical to the workflow's — same images, same tags,
same overlay edit — so a later CI-built deploy picks up seamlessly.
Needs `docker login ghcr.io` with a `write:packages` PAT, `kustomize`
on PATH, and roughly 15GB of free Docker disk.

### First deploy only

The very first deploy has more to do: pull seven images, run `initdb`,
and walk all 108 Prisma migrations. Give it 20 minutes before concluding
anything is wrong, and watch the migration Job specifically:

```bash
kubectl -n esoqo-preview get jobs
kubectl -n esoqo-preview logs -l app.kubernetes.io/name=migrate -f
```

## 5. Promoting to production

Production is a fast-forward of an already-green preview. It is never
built from a branch that preview has not run.

```bash
# 1. confirm preview is actually healthy — not just deployed
kubectl -n esoqo-preview get pods
curl -sS https://preview.esoko.global/api/health

# 2. promote — the deploy branch is `production`.
git checkout production && git pull
git merge --ff-only preview    # refuses if they have diverged — see
                                # CONTRIBUTING.md §2, they currently have
git push
```

If `--ff-only` refuses, the branches have diverged. Resolve that
deliberately — do not force it. See `CONTRIBUTING.md` §2 for the
current, real divergence as of 2026-09-27.

Pushing to `production` is supposed to trigger the same pipeline
against the production overlay, rebuilding images because
`NEXT_PUBLIC_*` differ — see [§7](#7-why-images-are-not-promoted) — but
per the note at the top of this file, nothing is actually watching that
push right now. Run `deploy/scripts/build-and-push.sh production` and
`kubectl apply -k deploy/k8s/overlays/production` yourself; see
`CONTRIBUTING.md` §5.

Then verify, in this order:

```bash
kubectl -n esoqo-production rollout status deploy/web --timeout=10m
curl -sS https://esoqo.com/api/health
curl -sS https://api.esoqo.com/ready      # walks the audit chain
```

## 6. Rollback

Because the overlay records the exact image tag, rollback is a revert:

```bash
git checkout production
git log --oneline -- deploy/k8s/overlays/production/kustomization.yaml
git revert <the-bad-deploy-commit>
git push
```

Fleet applies the previous tags within 60s. Nothing needs rebuilding —
the old images are still in GHCR.

**When speed matters more than tidiness**, roll the Deployment back
directly and then immediately commit the equivalent revert (otherwise
Fleet's drift correction undoes you within the minute):

```bash
kubectl -n esoqo-production rollout undo deploy/web
```

> A revert rolls back **code**, not **schema**. If the bad release
> included a destructive migration, reverting the image leaves the old
> code facing a new schema. See [§8](#8-breaking-schema-changes).

## 7. Why images are not promoted

`next build` inlines every `NEXT_PUBLIC_*` value into the client
JavaScript bundle. There is no runtime override — by the time the pod
starts, `https://preview.esoko.global` is a string literal in the
shipped JS.

So an image built for preview can never serve production: it would tell
browsers to call the preview API, and auth would fail in ways that look
like cookie bugs. Both environments build from the same commit with
different build args, producing different images with the same source.

The practical consequence: **the artifact tested on preview is not
byte-identical to the one running in production.** What is guaranteed
identical is the source commit and the build process. If that guarantee
ever becomes insufficient, the fix is to move those values to a runtime
config endpoint — not to promote the image.

## 8. Breaking schema changes

The migration `Job` and the app `Deployment`s are applied by Fleet in the
same pass. Nothing sequences them. For **additive** migrations (a new
table, a new nullable column) that is fine: old pods ignore what they do
not know about.

For a **destructive** migration (dropping or renaming a column,
tightening a constraint) it is not — old and new pods run side by side
during the rollout, and one of them will be wrong. Use expand/contract
across two releases:

**Release 1 — expand.** Add the new column. Write to both old and new.
Read from old. Deploy. Backfill:

```bash
kubectl -n esoqo-production exec -it deploy/core-service -- \
  pnpm --filter @esoqo/db backfill:<script>
```

**Release 2 — contract.** Switch reads to the new column, stop writing
the old one, and only now drop it.

Two releases is the cost of not taking an outage. Before either, take a
manual backup ([§10](#10-backups-and-restore)).

## 9. TLS, proxying and Access

The zone is on Cloudflare and the preview hosts are **Proxied**
(orange-cloud). Cloudflare Access (email one-time PIN) gates the five
UI hosts, so preview is not reachable by the public even though the DNS
records are public.

### Granting and revoking preview access

Access matches the address a visitor signs in with against the
**`Esoqo Preview`** application's `Allowed preview users` policy
(decision `allow`, rule = an *email* include list). Two things must
both be true for a login to succeed.

**1. The account has at least one login method.** Cloudflare Access
ships with **zero** identity providers; with none configured the login
page still renders but every attempt errors with *"There are no login
methods available for this account."* This account uses the built-in
**One-time PIN** provider (no external IdP, no per-seat cost) — create
it once:

```bash
CF_TOKEN=<token from .private/keys-secrets/cloudflare-notes.txt>
ACCT=e9a4f6bbf65d4e50e8a95ee3ce70b948

curl -sS -X POST \
  "https://api.cloudflare.com/client/v4/accounts/$ACCT/access/identity_providers" \
  -H "Authorization: Bearer $CF_TOKEN" -H "Content-Type: application/json" \
  --data '{"name":"One-time PIN","type":"onetimepin","config":{}}'
```

Take about 40s to propagate before relying on it.

**2. The email is on the policy.** Adding or removing people is a
policy edit — no redeploy, no DNS change, no image rebuild. The
identifiers live in the Terraform-free setup notes and can be read back
from the API:

```bash
APP=f29bf27a-3d63-4215-b11c-71b0edd877d0   # Esoqo Preview
POLICY=90e1f3d8-2e29-4aeb-9127-eead615b6034 # Allowed preview users
```

Dashboard: **Zero Trust → Access → Applications → Esoqo Preview →
`Allowed preview users` → Edit**, then `Include → Emails` and add the
address. Via API, `PUT` the policy with the **full** replacement list
(the `include` array is overwritten wholesale — resend every address):

```bash
curl -sS -X PUT \
  "https://api.cloudflare.com/client/v4/accounts/$ACCT/access/apps/$APP/policies/$POLICY" \
  -H "Authorization: Bearer $CF_TOKEN" -H "Content-Type: application/json" \
  --data '{"name":"Allowed preview users","decision":"allow","include":[
    {"email":{"email":"emmanuelodero808@gmail.com"}},
    {"email":{"email":"someone-else@example.com"}}
  ]}'
```

Each listed address then signs in with a 6-digit PIN emailed by Access
(the PIN is the login method; there is no password). Only addresses on
the list get a code.

**Verify** by curling a UI host and expecting a `302` to
`…cloudflareaccess.com/cdn-cgi/access/login/…`, not a `200`:

```bash
curl -sS -o /dev/null -w '%{http_code} %{redirect_url}\n' \
  https://preview.esoko.global/
```

> **Gotcha (already hit once):** the application's
> `self_hosted_domains` must be a real JSON **array**
> (`["preview.esoko.global","preview-app.esoko.global", …]`). A
> comma-separated *string* is stored as a single bogus element and
> Access matches nothing — the hosts then answer `200` to the public
> while the dashboard looks correct.

Origin certificates are issued by cert-manager over ACME **DNS-01**
(Cloudflare solver), via a namespaced `Issuer` per environment (see §3.2
— not a `ClusterIssuer`, despite the annotation name). HTTP-01 is not
usable here: Access intercepts every path on the host, including
`/.well-known/acme-challenge/`, so the challenge could never complete.
DNS-01 writes a `_acme-challenge` TXT record through the Cloudflare API
instead. The solver reads its token from the `cloudflare-api-token`
Secret (key `api-token`); create-secrets.sh builds it from
`CLOUDFLARE_API_TOKEN`. Set **SSL/TLS mode to Full (strict)** once the
origin certs are valid; during a first bootstrap leave it on **Full** so
a missing origin cert fails soft rather than with an edge 5xx.

**One-level hostnames only.** The Free plan's Universal SSL covers
`esoko.global` + `*.esoko.global` (one label). `app.preview.esoko.global`
is two labels deep and cannot be proxied, which is why every preview host
is `preview-<app>.esoko.global`.

**HTTP-01 cannot issue wildcard certificates**, hence the explicit host
lists in `ingress.yaml`. Adding a new app means adding an ingress rule, a
TLS host, an A record, and — if it is user-facing — an Access application.

**Start on staging.** Let's Encrypt rate-limits production issuance to 5
failures per hostname per hour, and a wrong token or zone burns through
that in minutes — after which the real certificate cannot issue for an
hour no matter what you fix. Swap the annotation in `ingress.yaml`:

```yaml
cert-manager.io/issuer: letsencrypt-staging
```

Deploy, confirm a certificate is issued (the browser will warn — that is
expected and correct for staging), then switch to `letsencrypt-prod`.
In practice this takes well under two minutes per environment once DNS
actually resolves to the cluster.

Check progress:

```bash
kubectl -n esoqo-preview get certificate
kubectl -n esoqo-preview describe certificate esoqo-preview-tls
kubectl -n esoqo-preview get challenge   # empty once issued
```

**If a Certificate stays `False` with events that never appear at
all** (not even a `DoesNotExist`/`Issuing` message updating) — check
whether the Ingress it's attached to predates ever being applied via
`kubectl apply` (e.g. it was originally created through Rancher's
browser Import-YAML flow). If so, the live object can end up with
*both* `cert-manager.io/cluster-issuer` and `cert-manager.io/issuer`
annotations set simultaneously — `kubectl apply`'s merge only *adds*
keys present in the new manifest, it can't remove one the live object
already has that your file no longer mentions. cert-manager then keeps
honoring the stale `cluster-issuer` key. Fix by deleting it explicitly:
`kubectl annotate ingress <name> -n <ns> cert-manager.io/cluster-issuer-`
(trailing dash = delete).

If a wildcard certificate ever becomes necessary — many dynamic Jamii
subdomains, say — switch the solver to `dns01` now that the zone is
already on Cloudflare (a token already exists for Jamii custom
domains).

## 9a. The cluster runs Traefik, not nginx

k3s ships Traefik by default, and this cluster is k3s. **Both overlays'
`ingress.yaml` already set `ingressClassName: traefik`** — confirmed
empirically during preview's bootstrap (an `nginx` class got a
controller-less 404 from every node; `traefik` routed within seconds)
and unchanged since. This used to be a hypothetical "if" in this doc;
it no longer is.

What's still true and still bites: the manifests carry legacy
`nginx.ingress.kubernetes.io/*` annotations that **Traefik silently
ignores**. Nothing errors; the behaviour just isn't there:

| Intent | nginx annotation | Traefik equivalent |
|---|---|---|
| 11MB Server Action uploads | `proxy-body-size: 12m` | a `Middleware` with `buffering.maxRequestBodyBytes` |
| `www` → apex redirect | `from-to-www-redirect: "true"` | a `Middleware` with `redirectRegex` |
| `noindex` on preview | `configuration-snippet` | a `Middleware` with `headers.customResponseHeaders` |

Losing the first one is the one that bites: uploads over 1MB fail with
a 413 from the proxy, and `apps/app` is built around 10MB document
uploads. Traefik's own default body limit is unlimited, so in practice
uploads work — but nothing is enforcing the 12MB ceiling either.

**The Traefik `Middleware` CRD needs cluster-scoped RBAC the
namespace-only account doesn't have** (`kubectl auth can-i create
middlewares.traefik.io` → `no`, confirmed 2026-09-27) — same shape of
problem as `ClusterIssuer` in §3.2. Until that access exists, the
practical workaround for the `www` case is routing `www.esoqo.com` to
the same backend as the apex directly in `ingress.yaml` (already done)
rather than a real 301 — it serves instead of 404ing, but both
hostnames now serve identical content with no canonical-URL signal to
browsers or crawlers. Fix properly (a real `Middleware`-based redirect)
once cluster-admin access exists.

`deploy/scripts/preflight.sh` reports the available IngressClasses, so
run it before assuming either way.

## 10. Backups and restore

A `CronJob` dumps Postgres nightly at 01:17 Africa/Nairobi, verifies the
dump is readable with `pg_restore --list`, then prunes anything older
than 14 days. Verification happens *before* pruning, so a failing dump
never costs you the previous good one.

Take one manually before any risky migration:

```bash
kubectl -n esoqo-production create job --from=cronjob/postgres-backup \
  manual-$(date +%s)
```

List what exists. The `postgres-backups` PVC is mounted only by the
CronJob's pods, so this runs a throwaway pod against it rather than
exec'ing into a running workload:

```bash
kubectl -n esoqo-production run backup-ls --rm -it --restart=Never \
  --image=busybox --overrides='{
    "spec": {
      "containers": [{
        "name": "backup-ls", "image": "busybox",
        "command": ["ls","-lh","/backups"],
        "volumeMounts": [{"name":"b","mountPath":"/backups"}]
      }],
      "volumes": [{"name":"b","persistentVolumeClaim":{"claimName":"postgres-backups"}}]
    }
  }'
```

### Restoring

This destroys data. `deploy/scripts/restore-job.yaml` is a template you
edit and apply by hand — deliberately not managed by Fleet, so no commit
can ever trigger it.

```bash
# 1. pause Fleet, or drift correction scales the apps back up
#    underneath the restore
kubectl -n fleet-default patch gitrepo production \
  --type merge -p '{"spec":{"paused":true}}'

# 2. stop everything that writes
kubectl -n esoqo-production scale deploy --all --replicas=0

# 3. edit BACKUP_FILE in the manifest, then run it. The Job verifies
#    the dump is readable BEFORE it drops anything.
kubectl -n esoqo-production apply -f deploy/scripts/restore-job.yaml
kubectl -n esoqo-production logs -f job/postgres-restore

# 4. bring it back, then unpause, then clean up
kubectl -n esoqo-production scale deploy --all --replicas=2
kubectl -n fleet-default patch gitrepo production \
  --type merge -p '{"spec":{"paused":false}}'
kubectl -n esoqo-production delete job postgres-restore
```

**Unpause the moment you are done.** A paused GitRepo is a cluster that
has silently stopped deploying.

### Backup gaps

These are known and currently open:

- **Backups live on a PVC in the same cluster.** That covers a bad
  migration or a mistaken `DELETE`. It does **not** cover cluster or
  storage loss. Shipping the dumps to off-cluster object storage (R2
  credentials already exist) is the outstanding fix.
- **No point-in-time recovery.** A nightly dump means up to 24 hours of
  loss. PITR needs WAL archiving, which in practice means moving to an
  operator like CloudNativePG.
- **Restores are untested.** A backup you have never restored is a
  hypothesis. Restore into preview at least once per quarter.

## 11. Troubleshooting

**`ImagePullBackOff`** — GHCR packages are private. See [§3.7](#37-ghcr-package-visibility).

**Pods `CrashLoopBackOff` right after a secret change** — `envFrom` does
not hot-reload. `kubectl rollout restart deploy -n <ns>`.

**Certificate stuck `False`/pending** — DNS is not resolving publicly
yet, or the ingress class name is wrong. `kubectl describe challenge -n <ns>`
names the actual reason.

**Fleet bundle stuck `Modified`** — a field Kubernetes defaults
server-side is being seen as drift. Add it to `diff.comparePatches` in
that overlay's `fleet.yaml`.

**Migration Job fails with an advisory-lock error** — two migration Jobs
ran at once, or it is pointed at PgBouncer instead of direct Postgres.
Confirm the Job's `DATABASE_URL` resolves to `DIRECT_DATABASE_URL`.

**`core-go` CrashLoopBackOff, logs say "refusing to start"** — it
requires `FLEET_QR_SECRET` and (with any `MPESA_PROVIDER` other than
`console`) `MPESA_CALLBACK_SECRET`. Outside `APP_ENV=development` it
will not fall back to the dev values published in this repo, by design.
Both are required entries in `secrets.env.template`.

**A pod restarts instantly with `ERR_MODULE_NOT_FOUND: 'tsx'`** — the
core-service image must run with its WORKDIR at `/repo/services/core`,
not `/repo`. tsx is a devDependency of that package so pnpm does not
hoist it, and Node resolving from `/repo` will not find it. The
migration Job's `workingDir: /repo` is a deliberate exception.

**Image build fails with "Please install typescript and @types/node"**
— something set `NODE_ENV=production` in the build stage. pnpm honours
it and skips devDependencies, and those two live in the root
package.json. `docker/Dockerfile.next` passes `--prod=false` to prevent
exactly this; do not remove it.

**`pnpm install` fails in the image build with a lockfile error** —
`pnpm-lock.yaml` is out of date. Run `pnpm install` locally and commit
it; the build uses `--frozen-lockfile` deliberately.

**Everything is healthy but the browser calls the wrong API** — the
`NEXT_PUBLIC_*` build args in `build-images.yml` have drifted from the
overlay's `config.yaml`. They must match; change both.

**Changed `orchestrate.sh` or `Dockerfile.deployer`, but the deploy
still runs the old logic** — the deployer executes from a **pinned
image** (`ci-webhook-config`'s `DEPLOYER_IMAGE`), not from the repo,
and `envFrom` does not hot-reload. A push is handled by whatever image
the *running* `ci-webhook` was started with, so rebuild under a new
immutable tag, update the overlay, then apply it to the live cluster
**and** restart the webhook *before* the next push:

```bash
kubectl -n esoqo-preview apply -f deploy/k8s/overlays/preview/ci-webhook-config.yaml
kubectl -n esoqo-preview rollout restart deploy/ci-webhook
kubectl -n esoqo-preview exec deploy/ci-webhook -- printenv DEPLOYER_IMAGE
# production: same three commands with -n esoqo-production
```

Real example (2026-10-10): the production webhook was still on the
pre-`33b40f7` deployer, whose migrate-Job extraction matched
`^kind: Job$` against a whole multi-line record, so every production
deploy died at *"could not find the migrate Job in the rendered
overlay"* until the webhook was repointed at the rebuilt tag.

### Useful commands

```bash
kubectl -n esoqo-preview get pods -w
kubectl -n esoqo-preview logs -f deploy/web
kubectl -n esoqo-preview describe pod <pod>          # events explain pending
```

## 12. What is deliberately not automated

- **Secrets** are created by hand with `create-secrets.sh`. A cloned
  repo must not be enough to reach the database.
- **`ClusterIssuer` and the Traefik `Middleware` CRD** are cluster-scoped
  and the day-to-day account has no RBAC for them — see §3.2 and §9a.
  Namespaced `Issuer` is the working substitute for TLS; there is no
  substitute yet for the `www` redirect.
- **DNS** is on Cloudflare (`esoqo.com` and `esoko.global`). Records are
  added by hand via the Cloudflare dashboard, and mostly don't change.
- **Preview Access** (the One-time PIN login method and the allowed-email
  policy) is managed in Cloudflare One by hand — see §9.
- **The deployer image is pinned by tag.** Editing `orchestrate.sh` or
  `Dockerfile.deployer` has no effect until it is rebuilt, the overlay's
  `DEPLOYER_IMAGE` is bumped, and the running `ci-webhook` is repointed
  — see §11.
- **Database restores** require a human deciding to lose data.
