# Deploying Esoqo

This is the operational runbook for both environments. It is meant to be
followed literally — if a step here is wrong, fix the step, not just the
cluster.

---

## 1. The model in one paragraph

**A deploy is a commit.** Pushing to `esoko/testnet` builds images, writes
the new image tags into `deploy/k8s/overlays/testnet/kustomization.yaml`,
and commits that back. Rancher Fleet watches the branch and applies the
result to the cluster. Production works identically from the `production`
branch. Nothing deploys by running `kubectl apply` at a laptop, and
Fleet's drift correction will revert anything that tries. A rollback is
therefore `git revert`, and "what is running?" is answered by reading the
overlay at that branch's HEAD.

| | testnet | production |
|---|---|---|
| Branch | `esoko/testnet` | `production` |
| Namespace | `esoqo-testnet` | `esoqo-production` |
| Overlay | `deploy/k8s/overlays/testnet` | `deploy/k8s/overlays/production` |
| Apex host | `testnet.esoko.global` | `esoko.global` |
| SMS | `console` — logs, never sends | **live** |
| Payments | sandbox | **live** |
| Replicas | 1 each | 2 (1 for admin) |
| Postgres volume | 20Gi | 100Gi |

## 2. What runs

Seven workloads plus three stateful pieces, all in one namespace per
environment.

| Workload | Image | Port | Hostname (testnet) |
|---|---|---|---|
| `web` | `esoqo-web` | 3000 | `testnet.esoko.global` |
| `app` | `esoqo-app` | 3001 | `app.testnet.esoko.global` |
| `admin` | `esoqo-admin` | 3002 | `admin.testnet.esoko.global` |
| `store` | `esoqo-store` | 3003 | `store.testnet.esoko.global` |
| `jamii` | `esoqo-jamii` | 3004 | `jamii.testnet.esoko.global` |
| `core-service` | `esoqo-core-service` | 4000 | `api.testnet.esoko.global` |
| `core-go` | `esoqo-core-go` | 4100 | `mobile.testnet.esoko.global` |
| `postgres` | `postgres:16-alpine` | 5432 | *(in-cluster only)* |
| `pgbouncer` | `edoburu/pgbouncer` | 6432 | *(in-cluster only)* |
| `redis` | `redis:7-alpine` | 6379 | *(in-cluster only)* |

Apps connect through **PgBouncer** (`DATABASE_URL`). Prisma migrations,
`pg_dump` and the audit-chain walk connect **directly** to Postgres
(`DIRECT_DATABASE_URL`) because none of them survive transaction
pooling. Both URLs are generated by `create-secrets.sh` — do not
hand-write them.

## 3. One-time setup

Do this once per environment. It is the only part involving a browser.

### 3.1 Cluster prerequisites

In Rancher (<https://rancher.2lovelaces.io/>), on the target cluster:

0. **Check your own permissions first.** A Rancher kubeconfig carries
   only the rights your Rancher role grants, and a restricted role
   produces a kubeconfig that authenticates fine and then refuses
   everything — which reads like a broken manifest rather than a
   missing role. Verify before anything else:

   ```bash
   export KUBECONFIG=<downloaded kubeconfig>
   kubectl auth can-i create deployments --all-namespaces
   kubectl auth can-i create gitrepos.fleet.cattle.io -n fleet-default
   ```

   Both must print `yes`. If either prints `no`, you need the
   **Cluster Owner** role on this cluster (Rancher → Cluster → Members),
   or an admin-issued kubeconfig. Nothing below will work without it.

   Note that Fleet applies manifests with its OWN service account, so
   the GitRepo permission is what matters for ongoing deploys — but you
   still need workload permissions to run the preflight, create the
   secrets, and debug a bad rollout.

1. **Label the cluster.** Cluster → Edit Config → Labels. Add
   `env=testnet` (or `env=production`). The Fleet `GitRepo` selects on
   this label rather than naming the cluster, so replacing the cluster
   later does not mean editing the repo.
2. **Install ingress-nginx** if the cluster has no ingress controller.
   RKE2 ships one; k3s ships Traefik instead. Check:
   ```bash
   kubectl get ingressclass
   ```
   If the class is not named `nginx`, change `ingressClassName` in both
   overlays' `ingress.yaml` and in
   `deploy/cluster/cluster-issuer.yaml` to match.
3. **Install cert-manager.** Apps → Charts → cert-manager, with the
   "Install CRDs" option enabled.

### 3.2 ClusterIssuers

```bash
kubectl apply -f deploy/cluster/cluster-issuer.yaml
```

Both `letsencrypt-staging` and `letsencrypt-prod` are created. Start on
staging — see [§9](#9-tls-and-wildcards).

### 3.3 Git credentials for Fleet

The repo is private, so Fleet needs read access. Create a GitHub
fine-grained PAT with **Contents: read** on `esoko-254`, then, on the
**Rancher local cluster**:

```bash
kubectl -n fleet-default create secret generic esoqo-git-credentials \
  --from-literal=username=Emmanuel-Odero \
  --from-literal=password='<the-PAT>'
```

### 3.4 Register the GitRepo

Also on the Rancher local cluster:

```bash
kubectl apply -f deploy/fleet/gitrepo-testnet.yaml
# later, when production is ready:
kubectl apply -f deploy/fleet/gitrepo-production.yaml
```

Watch it in Rancher → **Continuous Delivery → Git Repos**.

### 3.5 Secrets

```bash
cp deploy/scripts/secrets.env.template ~/esoqo-testnet.secrets.env
# fill it in — every "required" field
deploy/scripts/create-secrets.sh testnet ~/esoqo-testnet.secrets.env
```

The script validates before touching the cluster, builds the connection
strings, and prints the kube context for confirmation first. Store the
filled-in file in a password manager and delete it from disk.

> `AUDIT_CHAIN_SEED` is set **once per environment and never rotated**.
> Changing it breaks the existing hash chain permanently and
> `audit:verify` will fail forever after. testnet and production must
> have different values.

### 3.6 DNS at Namecheap

Namecheap → Domain List → `esoko.global` → **Advanced DNS**.

First get the ingress IP:

```bash
kubectl -n ingress-nginx get svc ingress-nginx-controller \
  -o jsonpath='{.status.loadBalancer.ingress[0].ip}'
```

If that is empty, the controller is `NodePort` rather than
`LoadBalancer` — use a worker node's public IP instead:

```bash
kubectl get nodes -o wide
```

Then add these records. Two records cover all five testnet apps, because
the apex and the wildcard together match every hostname:

| Type | Host | Value | TTL |
|---|---|---|---|
| A | `testnet` | `<INGRESS_IP>` | 5 min |
| A | `*.testnet` | `<INGRESS_IP>` | 5 min |

And for production, when you get there:

| Type | Host | Value | TTL |
|---|---|---|---|
| A | `@` | `<INGRESS_IP>` | 5 min |
| A | `www` | `<INGRESS_IP>` | 5 min |
| A | `*` | `<INGRESS_IP>` | 5 min |

> The apex **must** be an A record. DNS forbids a CNAME at a zone apex,
> and Namecheap's "URL Redirect" workaround breaks the ACME HTTP-01
> challenge, so certificates will never issue.

Verify before expecting TLS to work — cert-manager cannot succeed until
these resolve publicly:

```bash
dig +short testnet.esoko.global
dig +short admin.testnet.esoko.global
```

### 3.7 GHCR package visibility

The first push creates the packages as **private**, and the cluster
cannot pull them. Either make them public
(github.com/users/Emmanuel-Odero/packages → each package → Package
settings → Change visibility), or create a pull secret in each
namespace:

```bash
kubectl -n esoqo-testnet create secret docker-registry ghcr \
  --docker-server=ghcr.io \
  --docker-username=Emmanuel-Odero \
  --docker-password='<PAT with read:packages>'
kubectl -n esoqo-testnet patch serviceaccount default \
  -p '{"imagePullSecrets":[{"name":"ghcr"}]}'
```

`ImagePullBackOff` on the first deploy is almost always this.

### 3.8 Branch protection

**Do not skip this for production.** `build-images.yml` runs in parallel
with `ci.yml`, so it is branch protection — not the workflow — that
stops untested code from shipping.

GitHub → Settings → Branches → add a rule for `production`:

- Require a pull request before merging
- Require status checks to pass: `verify`, `security`
- Do not allow bypassing

Then add a `DEPLOY_BOT_TOKEN` secret (a PAT that may push to the
protected branch), so the tag-bump commit can land.

## 4. Routine deploy to testnet

```bash
git checkout esoko/testnet
git pull
# ... work ...
git commit -m "feat(parcels): ..."
git push
```

That is the whole procedure. Then watch:

1. **GitHub → Actions → "Build and deploy"** — seven images build in
   parallel, then `bump` commits the new tags. ~8–12 min cold, ~3–4 min
   warm.
2. **Rancher → Continuous Delivery → Bundles** — `esoqo-testnet` goes
   `Modified` → `Ready` within the 60s poll.
3. Confirm:
   ```bash
   kubectl -n esoqo-testnet get pods
   kubectl -n esoqo-testnet rollout status deploy/web --timeout=5m
   curl -sS https://testnet.esoko.global/api/health
   ```

### Deploying without GitHub Actions

Fleet reads manifests straight from git, so Actions was never on the
critical path — it only builds the images and commits the tag bump.
`deploy/scripts/build-and-push.sh` does both from a laptop:

```bash
git checkout esoko/testnet        # the script refuses to run from another branch
deploy/scripts/build-and-push.sh testnet
git push origin esoko/testnet     # this is what Fleet reacts to
```

The output is identical to the workflow's — same images, same tags,
same overlay edit — so a later CI-built deploy picks up seamlessly.
Needs `docker login ghcr.io` with a `write:packages` PAT, `kustomize`
on PATH, and roughly 15GB of free Docker disk.

### First deploy only

The very first deploy has more to do: pull seven images, run `initdb`,
and walk all 108 Prisma migrations. Give it 20 minutes before concluding
anything is wrong, and watch the migration Job specifically:

```bash
kubectl -n esoqo-testnet get jobs
kubectl -n esoqo-testnet logs -l app.kubernetes.io/name=migrate -f
```

## 5. Promoting to production

Production is a fast-forward of an already-green testnet. It is never
built from a branch that testnet has not run.

```bash
# 1. confirm testnet is actually healthy — not just deployed
kubectl -n esoqo-testnet get pods
curl -sS https://testnet.esoko.global/api/health

# 2. open the promotion PR
git checkout production && git pull
git merge --ff-only esoko/testnet    # refuses if they have diverged
git push
```

If `--ff-only` refuses, the branches have diverged and something was
committed to `production` directly. Resolve that deliberately — do not
force it.

Pushing to `production` triggers the same pipeline against the
production overlay. Because `NEXT_PUBLIC_*` differ, the images are
**rebuilt**, not copied — see [§7](#7-why-images-are-not-promoted).

Then verify, in this order:

```bash
kubectl -n esoqo-production rollout status deploy/web --timeout=10m
curl -sS https://esoko.global/api/health
curl -sS https://api.esoko.global/ready      # walks the audit chain
```

## 6. Rollback

Because the overlay records the exact image tag, rollback is a revert:

```bash
git checkout production
git log --oneline -- deploy/k8s/overlays/production/kustomization.yaml
git revert <the-bad-deploy-commit>
git push
```

Fleet applies the previous tags within 60s. Nothing needs rebuilding —
the old images are still in GHCR.

**When speed matters more than tidiness**, roll the Deployment back
directly and then immediately commit the equivalent revert (otherwise
Fleet's drift correction undoes you within the minute):

```bash
kubectl -n esoqo-production rollout undo deploy/web
```

> A revert rolls back **code**, not **schema**. If the bad release
> included a destructive migration, reverting the image leaves the old
> code facing a new schema. See [§8](#8-breaking-schema-changes).

## 7. Why images are not promoted

`next build` inlines every `NEXT_PUBLIC_*` value into the client
JavaScript bundle. There is no runtime override — by the time the pod
starts, `https://testnet.esoko.global` is a string literal in the
shipped JS.

So an image built for testnet can never serve production: it would tell
browsers to call the testnet API, and auth would fail in ways that look
like cookie bugs. Both environments build from the same commit with
different build args, producing different images with the same source.

The practical consequence: **the artifact tested on testnet is not
byte-identical to the one running in production.** What is guaranteed
identical is the source commit and the build process. If that guarantee
ever becomes insufficient, the fix is to move those values to a runtime
config endpoint — not to promote the image.

## 8. Breaking schema changes

The migration `Job` and the app `Deployment`s are applied by Fleet in the
same pass. Nothing sequences them. For **additive** migrations (a new
table, a new nullable column) that is fine: old pods ignore what they do
not know about.

For a **destructive** migration (dropping or renaming a column,
tightening a constraint) it is not — old and new pods run side by side
during the rollout, and one of them will be wrong. Use expand/contract
across two releases:

**Release 1 — expand.** Add the new column. Write to both old and new.
Read from old. Deploy. Backfill:

```bash
kubectl -n esoqo-production exec -it deploy/core-service -- \
  pnpm --filter @esoqo/db backfill:<script>
```

**Release 2 — contract.** Switch reads to the new column, stop writing
the old one, and only now drop it.

Two releases is the cost of not taking an outage. Before either, take a
manual backup ([§10](#10-backups-and-restore)).

## 9. TLS and wildcards

Certificates are issued by cert-manager over ACME **HTTP-01**. That
needs nothing but a publicly reachable ingress — no registrar API
credentials — which matters because the domain is at Namecheap and
cert-manager ships no Namecheap DNS solver.

The tradeoff: **HTTP-01 cannot issue wildcard certificates.** Hence the
explicit host lists in both overlays' `ingress.yaml`. DNS is still
wildcard, so adding a sixth app means adding a rule and a `tls.hosts`
entry — and no DNS change.

**Start on staging.** Let's Encrypt rate-limits production issuance to 5
failures per hostname per hour, and a wrong A record burns through that
in minutes — after which the real certificate cannot issue for an hour
no matter what you fix. Swap the annotation in `ingress.yaml`:

```yaml
cert-manager.io/cluster-issuer: letsencrypt-staging
```

Deploy, confirm a certificate is issued (the browser will warn — that is
expected and correct for staging), then switch to `letsencrypt-prod`.

Check progress:

```bash
kubectl -n esoqo-testnet get certificate
kubectl -n esoqo-testnet describe certificate esoqo-testnet-tls
kubectl -n esoqo-testnet get challenge   # empty once issued
```

If a wildcard certificate ever becomes necessary — many dynamic Jamii
subdomains, say — the path is to move the zone's DNS to Cloudflare (a
token already exists for Jamii custom domains) and switch the solver to
`dns01`.

## 10. Backups and restore

A `CronJob` dumps Postgres nightly at 01:17 Africa/Nairobi, verifies the
dump is readable with `pg_restore --list`, then prunes anything older
than 14 days. Verification happens *before* pruning, so a failing dump
never costs you the previous good one.

Take one manually before any risky migration:

```bash
kubectl -n esoqo-production create job --from=cronjob/postgres-backup \
  manual-$(date +%s)
```

List what exists. The `postgres-backups` PVC is mounted only by the
CronJob's pods, so this runs a throwaway pod against it rather than
exec'ing into a running workload:

```bash
kubectl -n esoqo-production run backup-ls --rm -it --restart=Never \
  --image=busybox --overrides='{
    "spec": {
      "containers": [{
        "name": "backup-ls", "image": "busybox",
        "command": ["ls","-lh","/backups"],
        "volumeMounts": [{"name":"b","mountPath":"/backups"}]
      }],
      "volumes": [{"name":"b","persistentVolumeClaim":{"claimName":"postgres-backups"}}]
    }
  }'
```

### Restoring

This destroys data. `deploy/scripts/restore-job.yaml` is a template you
edit and apply by hand — deliberately not managed by Fleet, so no commit
can ever trigger it.

```bash
# 1. pause Fleet, or drift correction scales the apps back up
#    underneath the restore
kubectl -n fleet-default patch gitrepo esoqo-production \
  --type merge -p '{"spec":{"paused":true}}'

# 2. stop everything that writes
kubectl -n esoqo-production scale deploy --all --replicas=0

# 3. edit BACKUP_FILE in the manifest, then run it. The Job verifies
#    the dump is readable BEFORE it drops anything.
kubectl -n esoqo-production apply -f deploy/scripts/restore-job.yaml
kubectl -n esoqo-production logs -f job/postgres-restore

# 4. bring it back, then unpause, then clean up
kubectl -n esoqo-production scale deploy --all --replicas=2
kubectl -n fleet-default patch gitrepo esoqo-production \
  --type merge -p '{"spec":{"paused":false}}'
kubectl -n esoqo-production delete job postgres-restore
```

**Unpause the moment you are done.** A paused GitRepo is a cluster that
has silently stopped deploying.

### Backup gaps

These are known and currently open:

- **Backups live on a PVC in the same cluster.** That covers a bad
  migration or a mistaken `DELETE`. It does **not** cover cluster or
  storage loss. Shipping the dumps to off-cluster object storage (R2
  credentials already exist) is the outstanding fix.
- **No point-in-time recovery.** A nightly dump means up to 24 hours of
  loss. PITR needs WAL archiving, which in practice means moving to an
  operator like CloudNativePG.
- **Restores are untested.** A backup you have never restored is a
  hypothesis. Restore into testnet at least once per quarter.

## 11. Troubleshooting

**`ImagePullBackOff`** — GHCR packages are private. See [§3.7](#37-ghcr-package-visibility).

**Pods `CrashLoopBackOff` right after a secret change** — `envFrom` does
not hot-reload. `kubectl rollout restart deploy -n <ns>`.

**Certificate stuck `False`/pending** — DNS is not resolving publicly
yet, or the ingress class name is wrong. `kubectl describe challenge -n <ns>`
names the actual reason.

**Fleet bundle stuck `Modified`** — a field Kubernetes defaults
server-side is being seen as drift. Add it to `diff.comparePatches` in
that overlay's `fleet.yaml`.

**Migration Job fails with an advisory-lock error** — two migration Jobs
ran at once, or it is pointed at PgBouncer instead of direct Postgres.
Confirm the Job's `DATABASE_URL` resolves to `DIRECT_DATABASE_URL`.

**`core-go` CrashLoopBackOff, logs say "refusing to start"** — it
requires `FLEET_QR_SECRET` and (with any `MPESA_PROVIDER` other than
`console`) `MPESA_CALLBACK_SECRET`. Outside `APP_ENV=development` it
will not fall back to the dev values published in this repo, by design.
Both are required entries in `secrets.env.template`.

**A pod restarts instantly with `ERR_MODULE_NOT_FOUND: 'tsx'`** — the
core-service image must run with its WORKDIR at `/repo/services/core`,
not `/repo`. tsx is a devDependency of that package so pnpm does not
hoist it, and Node resolving from `/repo` will not find it. The
migration Job's `workingDir: /repo` is a deliberate exception.

**Image build fails with "Please install typescript and @types/node"**
— something set `NODE_ENV=production` in the build stage. pnpm honours
it and skips devDependencies, and those two live in the root
package.json. `docker/Dockerfile.next` passes `--prod=false` to prevent
exactly this; do not remove it.

**`pnpm install` fails in the image build with a lockfile error** —
`pnpm-lock.yaml` is out of date. Run `pnpm install` locally and commit
it; the build uses `--frozen-lockfile` deliberately.

**Everything is healthy but the browser calls the wrong API** — the
`NEXT_PUBLIC_*` build args in `build-images.yml` have drifted from the
overlay's `config.yaml`. They must match; change both.

## 12. What is deliberately not automated

- **Secrets** are created by hand with `create-secrets.sh`. A cloned
  repo must not be enough to reach the database.
- **ClusterIssuers and ingress-nginx** are cluster-scoped and shared, so
  neither environment's bundle should own them.
- **DNS** is at Namecheap with no API integration. Records are added by
  hand, and they change roughly never.
- **Database restores** require a human deciding to lose data.
